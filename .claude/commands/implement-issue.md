引数: ユーザーがコマンド名の直後にチャットで渡した Issue 番号（Claude Code では自動展開される）。以下「上記引数」と呼ぶ。

GitHub Issue #上記引数 を、`AGENTS.md` の安全ガードレールを守って実装する。

## 手順
1. **Issue を読む**: `gh issue view <上記引数>` で背景・タスク・受け入れ条件・参照 § を取得。
2. **仕様を読む**: Issue が参照する `docs/system_requirements.md` の該当 § を必ず開いて読む。`AGENTS.md` の安全ガードレールも再確認。
3. **計画**: 変更するファイル・追加するテストを箇条書きで提示し、実装前に確認を取る。
4. **ブランチ**: **`origin/main` 起点**で `feature/E<番号>-<短い説明>` を切る
   （例: `git switch -c feature/E<n>-... origin/main`。ローカル main の鮮度に依存しない）。
5. **実装**: 規約（型注釈・ruff/black・構造化ログ）に従う。エンドポイントは定数経由、署名パスは `/v1/...`。
6. **テスト**: ユニットテストを書き `pytest` 緑を確認。署名・発注系は特に手厚く。
7. **外部依存の裏取り（推測禁止）**:
   - GMO FX API の未確定フィールド → スパイクで実レスポンスを確認し、仕様書「付録B」に追記。
   - ライブラリ / SDK / クラウドサービス（AWS 等）の非自明な挙動（名前・シグネチャ・形式・制約・既定値・条件のセマンティクス）→ 記憶や推測で書かず**公式一次情報で裏取り**し、依存箇所に出典 URL（参照日付き）を残す。
8. **DoD チェック**（`AGENTS.md`）: 受け入れ条件充足 / テスト緑 / ガードレール違反なし / 付録B反映 / 外部依存は公式一次情報で裏取り・出典URL記載 / PR に Issue番号・§。
9. **PR（この手順の完了条件・追加確認不要）**: コミットに続けて `gh pr create --base main` まで必ず実行する。
   本文に `Closes #<上記引数>` と参照 § を記載。ユーザーの再確認を待って止まらないこと。

## 厳守
- Phase 1 では発注系 POST を実送信しない（スタブ）。
- 1 Issue = 1 PR。スコープ外の変更を混ぜない。
